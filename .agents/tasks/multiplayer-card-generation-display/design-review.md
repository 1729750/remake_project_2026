# Design Review: Multiplayer Card Generation and Display

## Verdict Summary

**CHANGES_REQUESTED**. The plan has a strong owner-scoped snapshot and input-state design, and it correctly identifies most existing gaps. However, it contains blocking implementation details that can produce incorrect card behavior or fail before the stated validation runs. The HIGH and MEDIUM findings below must be resolved before implementation.

## HIGH

1. **HIGH - Runtime snapshot reconstruction loses effect semantics.** The plan's `PreparationStateSnapshot` section specifies reconstructing each effect with `new CardEffect(new Effect(type, magnitude), target)` and then setting `AppliedCategory`. In this project, `CardEffect.GetSupportedCategories()` explicitly recreates the concrete effect through `Effect.Create(effectType, 0)`, and `CardDefinition` validates card type/category against that supported-category behavior. A base `new Effect(...)` is not a faithful reconstruction contract for effect subclasses and can change supported categories or later battle behavior. **Concrete fix:** define the reconstruction factory as `Effect.Create(effectType, magnitude)` (or a single shared factory that is explicitly verified to preserve every concrete `EffectType`), then construct `CardEffect`, set target and applied category, and reject any unsupported/unknown type. Add a round-trip rule that the reconstructed effect's type, magnitude, target, supported category, and applied category must equal the server record before the UI swap.

2. **HIGH - The proposed serialized-effects validation cannot safely inspect malformed definitions.** In section (A), the plan requires rejecting null effect lists and null `CardEffect`/underlying effects, but the existing public `CardDefinition.GetEffects()` calls `_effects.ToArray()` and throws when `_effects` is null. The plan does not define a safe accessor or editor/runtime validation boundary, so the required configuration rejection cannot be implemented as described. **Concrete fix:** add a narrowly scoped `CardDefinition.TryGetValidatedEffects(out CardEffect[] effects, out string reason)` that checks the backing list and every nested object before returning a copy, or add an equivalent internal validation API in `CardDefinition`; require all pool validation and snapshot export to use it and catch/report invalid enum/category data without allowing an exception to escape the server request path.

3. **HIGH - Candidate and upper-display data contracts are not fully separated at the model level.** The plan says candidates use the existing candidate panel while the upper panel uses cumulative owner cards, but `PreparationOption` still carries a `CardDefinition Card`, and the proposed `FromNetData` client reconstruction is described as making a clone from the shared pool. It does not specify the exact rule for an `EnhanceCard` candidate's target card data, nor how the client obtains the owner snapshot's already-mutated card without treating it as a candidate. This risks displaying a source-pool definition or a target card before/after the wrong commit. **Concrete fix:** define two explicit DTO contracts: `PreparationOptionNetData` for candidate metadata (`AddCard` has immutable `CardPoolIndex`; `EnhanceCard` has only validated target index/upgrade id; `Skip` has neither), and `SelectedCardNetData` for committed owner cards (all runtime values/effects). State that candidate visuals never read `SelectedCards`, and upper visuals never read `PreparationOption.Card`; apply the snapshot only after atomic reconstruction succeeds.

4. **HIGH - The RPC migration is ambiguous relative to the current NGO implementation.** The plan says to unify responses into a “legacy server-only ClientRpc” and gives a `ClientRpcParams` example, while the current `NetworkMatchBridge` uses `[Rpc(SendTo.Server)]` requests and `[Rpc(SendTo.ClientsAndHost)]` responses with a manual `targetClientId` filter. The plan does not specify the exact NGO attribute/signature transition, whether the legacy API is enabled for this package/version, or how the existing `SendPreparationOptionsRpc` and `SendPreparationConfirmResultRpc` are removed/replaced. A partial migration can leave both paths active or compile against the wrong RPC API. **Concrete fix:** choose one API for NGO `2.13.0` and name the exact declarations to retain/delete. If using legacy `[ClientRpc]`, specify the exact `ClientRpcParams` signature and replace every current response call site; if using universal `[Rpc]`, use the package's supported targeted `BaseRpcTarget` API and remove payload-level target filtering. Add a static acceptance check that no preparation response contains another client's options, deck, or snapshot.

## MEDIUM

5. **MEDIUM - Scene-local PopupManager copying is not sufficiently feasible or bounded.** Section (B) requires copying `PopupManager.prefab` contents into scene-local records because its `.meta` has conflict markers, while also retaining nested `PopUpComponent` prefab structure and remapping stripped/prefab references. The plan does not define whether the resulting scene-local objects are ordinary scene objects or valid prefab instances, nor how `PopupManager.Awake`'s child search is guaranteed to find inactive nested children after the copy. This is a high-risk hand-authored YAML edit and can silently produce missing references despite the claimed static checks. **Concrete fix:** choose one representation: either (a) create a fully scene-local ordinary hierarchy with no `m_CorrespondingSourceObject`/`m_PrefabInstance` links and explicitly bind every component, or (b) use only the valid `PopUpComponent.prefab` instance and a new clean PopupManager prefab/meta created outside the conflicted asset. Document the exact root/component fields and a check that `PopupManager` discovers at least one `PopupComponent` while inactive and initializes it after activation.

6. **MEDIUM - The plan does not define the existing-deck source-index failure path precisely enough.** It correctly says not to guess when an initial card cannot be mapped to the pool, but the design still requires `SelectedCards` to serialize `SourceCardPoolIndex` and says initial deck metadata should be recorded. It does not define when that metadata is created, what happens to an existing runtime clone whose source index is unavailable, or whether preparation is blocked before the first candidate is shown. **Concrete fix:** at server preparation initialization, validate every initial deck card and build immutable source metadata; if any card has no exact pool identity, reject preparation for that owner with a configuration error and send an empty/non-mutating error snapshot. Do not start generation or allow Add/Enhance/Skip until that validation succeeds.

7. **MEDIUM - The transition hook does not satisfy the requested transition contract unless its boundary is made explicit.** Section (E) adds `transitionDelaySeconds` and calls `MapManager_Multi.NotifyBothPlayersConfirmed()` after the delay, but the investigation verifies that this method immediately calls `GameManager_Multi.StartBattle()`, while the plan also says scene migration and FinalDeck handoff are out of scope. The resulting behavior is not clearly “move to the actual game mode” versus “start battle in the current preparation scene,” and the plan does not define what state prevents a second completion response from scheduling another transition. **Concrete fix:** state explicitly that this task only schedules one server-side delayed call to the existing `StartBattle` entry point, with no scene transition or FinalDeck handoff; add a server-only `transitionStarted`/`transitionCancelled` state that is set before starting the coroutine, cleared only on an explicit disconnect abort, and checked again after the delay. Do not describe this as completing step 11 or FinalDeck integration.

8. **MEDIUM - Pool validation claims are not tied to the actual serialized source of truth.** The plan requires the Multi generator's 29-entry list to match `SinglePlayMode.unity:2388` “in the same order,” but the verified Single producer reads `RewardManager.GetRewardCards()` in `GameManager.GenerateRandomEnemy()`, not a generator list. The plan must distinguish the Single scene's RewardManager reference from the Multi scene's CardOptionGenerator reference and define how equality is established. **Concrete fix:** state that the canonical sequence is `RewardManager.rewardCards` as returned by `GetRewardCards()` on the Single scene, identify the exact serialized field/component used to read it, and validate count, GUID, and order against the Multi `cardPool` at edit/runtime configuration validation. Do not use the scene line number alone as the contract.

## LOW

9. **LOW - The plan's “Single semantics” wording is broader than the actual requested display path.** `DeckDisplay.SpawnCard` does use `CardInstance(def, null) -> SetVisual -> SetFace(true) -> SetLayer("UI")`, and `MapManager.RefreshDeckSelectionPopup` preserves effect order, but the current `DeckDisplay` defaults to four columns and the plan introduces six-column/scale behavior. **Concrete fix:** call the reused path “same data and popup path, with Multi-specific layout parameters,” and keep the layout change isolated to Multi scene bindings/configuration.

10. **LOW - Cleanup ownership is described but not assigned to a concrete lifecycle owner.** The plan requires destroying candidate and snapshot clones at replacement, cancel, scene unload, and `OnDestroy`, but does not identify whether `MapManager_Multi`, the snapshot DTO owner, or the preparation manager owns each clone. **Concrete fix:** state that server runtime deck clones belong to `PlayerPreparationData` until registry removal, while client display clones belong to `MapManager_Multi`; only those owners perform cleanup.

## Verified Assumptions

- Single random enemy generation is `GameManager.GenerateRandomEnemy(...)`, using `RewardManager.GetRewardCards()`, `Random.Range(8, 13)`, duplicate-allowed random selection, and `source.Clone()` for every generated card.
- Single card display uses `DeckDisplay.SpawnCard`: `CardVisual`, `new CardInstance(def, null)`, `SetVisual`, `SetFace(true)`, and `SetLayer("UI")`.
- Single deck detail popup derives an ordered list of every selected card's `EffectType` from `CardDefinition.GetEffects()` and calls the screen's `PopupManager.Show(...)`.
- `CardDefinition.Clone()` deep-copies `CardEffect` and `Effect` values and shares the sprite reference; `CardDefinition.ApplyUpgrade()` mutates the clone.
- Current Multi preparation state is keyed by actual `ulong clientId` in `currentRoundByClient` and `currentOptionsByClient`, but current confirm/skip response delivery is unfinished in `NetworkMatchBridge`.
- Current Multi `ApplyEnhance()` validates only the target index and does not mutate the card.
- Current `MapManager_Multi.myDeckDisplay` is unbound in the investigated scene, and the current upper-display path is incomplete.
- The plan explicitly keeps Single behavior, `.git`, and `Assets/_Recovery` out of scope.

## Unverified/Wrong Assumptions

- **Wrong as written:** reconstructing an effect with base `new Effect(type, magnitude)` is equivalent to the project's concrete effect factory. The source code's `Effect.Create(...)` and supported-category logic make that unsafe.
- **Unverified:** the 29 listed GUIDs are exactly the same ordered sequence as the Single scene's `RewardManager.rewardCards`; the plan names the sequence but does not provide a machine-checkable source-field comparison contract.
- **Unverified:** the conflicted PopupManager prefab can be copied into valid scene-local records with all nested prefab and stripped references intact. This needs the explicit representation and validation rule in finding 5.
- **Unverified:** all existing initial `FinalDeck` cards have exact source-pool identity metadata. The investigation only establishes that the current server list contains runtime clones for added cards; it does not establish source metadata for every initial card.
- **Unverified:** the selected NGO RPC API migration compiles and has no duplicate response path under package `2.13.0`; the plan must choose and specify one API.

## Verdict

**CHANGES_REQUESTED**. There are 4 HIGH and 4 MEDIUM findings. The review JSON is the loop stop-contract and therefore reports `CHANGES_REQUESTED`.
